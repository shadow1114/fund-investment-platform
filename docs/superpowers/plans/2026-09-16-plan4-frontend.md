# Plan-4 M1.7 Frontend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the M1.7 Vite/React frontend for fund research, universe snapshots, portfolio decisions, and backtests against the frozen `/api/v1` consumer contract.

**Architecture:** A TypeScript React shell owns routing and page composition. A generated API client is the only network boundary; TanStack Query owns server state and polling, while page components render domain data without duplicating business calculations. Shared provenance, metric/null, formatting, and explanation components enforce the frozen API semantics across all pages.

**Tech Stack:** Vite, React 18, TypeScript, TanStack Query, TanStack Table, ECharts, `openapi-typescript`, Orval, Vitest, Testing Library, MSW, ESLint, and Prettier.

**Spec:** `docs/superpowers/specs/2026-09-16-plan4-contract-freeze-design.md` and `docs/10-api/06-m17-frontend-contracts.md`

## Global Constraints

- The four M1.7 pages are fund research/detail, universe snapshot, portfolio decision, and backtest.
- The client consumes only the frozen `/api/v1` paths in `docs/10-api/06-m17-frontend-contracts.md` §2; paths outside that table are not added to the UI.
- OpenAPI 3.1.0 is the machine-readable projection of the frozen contract; generated client code is not hand-edited.
- Every response uses `{ data, meta, error }`; errors are rendered by status and reason, not converted to successful empty data.
- All long-running optimization and backtest commands return `202` and poll `GET /api/v1/operations/{operation_id}`.
- `null` metrics must render with their `status` and `reason`; never render `0`, `-`, or an empty string as a substitute.
- Percentages remain decimal values in transport and are multiplied by 100 only in display formatters.
- `meta.versions`, `meta.is_point_in_time`, and `availability_quality_distribution` remain visible in a provenance bar.
- `Approve`, `Reject`, and `Override` controls are visible only when `GET /api/v1/session` reports `can_review_decisions: true`; the server remains the authorization boundary.
- `INFEASIBLE`, `NOT_CONVERGED`, `INVALID`, `WARNING`, and unknown enum values remain distinguishable in the UI.
- `REJECTED` universe members and their failed conditions are displayed; the UI never filters them out silently.
- No business calculation, PIT decision, portfolio authorization, or trading execution is implemented in the frontend.
