## 2. 选型原则

### 2.1 六条原则

| # | 原则 | 含义 |
|---|---|---|
| P-1 | **可解释优先** | 技术行为可预期、可排查，优于"能力强但难以推理" |
| P-2 | **成熟稳定优先** | 选择有长期维护记录与广泛实践的技术 |
| P-3 | **易维护优先** | 团队能独立运维，不依赖小众专家 |
| P-4 | **支持批量计算** | 系统的主要负载是批量计算，而非高并发在线请求 |
| P-5 | **支持历史数据与审计** | 时点查询、版本管理、不可篡改记录是硬需求 |
| P-6 | **支持可复现** | 版本可固定、行为确定、无隐式状态 |

### 2.2 一条反原则

> **不为"技术先进"引入没有业务价值的技术。**

第一阶段是纯 Quant 基线，复杂度应投入**策略正确性**，而非基础设施。每引入一个组件，都要回答"不引入它会怎样"。

## 4. Database

### 4.1 选型：PostgreSQL

| 字段 | 内容 |
|---|---|
| **Technology** | PostgreSQL |
| **Purpose** | 承载**全部**持久化数据：基金主数据、净值序列、因子明细、评分、Peer Group / Universe 快照、Return Estimate、协方差、决策快照、配置与版本、审计记录、回测结果 |
| **Why Selected** | ① **满足最硬的约束**——决策快照需在单一事务内完整写入，关系型事务天然支持（见 §4.3）<br/>② **数据规模不构成引入列存的理由**——总量十亿行以内、几十 GB（见 §4.2）；**但性能达标须由 §4.6 的负载验证确认，不由行数推断**<br/>③ **时点查询友好**——三元时点 + 版本选择本质是带条件的关系查询<br/>④ **分区表支撑时序**——按时间分区可高效处理净值与因子明细<br/>⑤ 成熟稳定、运维门槛低、团队易掌握（P-2、P-3） |
| **Alternative** | PostgreSQL + ClickHouse 双库（原方案）；MySQL；时序数据库 |
| **Trade-offs** | 放弃列存带来的大规模聚合性能；因子明细的宽表扫描慢于列存数据库；未来数据量跃升时需重新评估 |
| **Current Phase** | 第一阶段唯一持久化存储 |
| **Future Consideration** | 见 §4.4 重评估触发条件 |

### 4.2 为什么不引入 ClickHouse

**依据一 · 数据规模远未进入列存收益区**

按中国公募约 1.2 万只基金、日频、10 年历史：

| 数据 | 行数估算 | 体量 |
|---|---|---|
| 净值序列 | 12,000 × 250 × 10 ≈ 3,000 万行 | ~1.5 GB |
| 因子值明细（50 因子） | 12,000 × 50 × 250 × 10 ≈ 1.5 亿行 | ~6 GB |
| Fund Score 历史 | ≈ 3,000 万行 | ~2 GB |
| 协方差 / 相关性矩阵 | 每决策时点一份，可整体序列化 | 可忽略 |
| 回测结果 | ≈ 400 万行 | ~0.3 GB |

总量**十亿行以内、几十 GB 级**。ClickHouse 解决的是 TB 级、百亿行、高并发聚合的问题。**基金是日频数据，比股票 tick 数据小三到四个数量级**。

> **但数据量只能否定"必须引入列存"，不能肯定"关系型一定够用"。**
>
> 性能取决于**查询模式**而非仅数据规模。同样 1.5 亿行的因子明细，"取单只基金单因子的时间序列"与"取全市场 50 个因子在某时点的横截面"是完全不同的负载，后者是典型的列存优势场景。
>
> 因此本选型的成立条件是：**§4.6 定义的关键负载必须通过实测验证**。未通过则触发 §4.4 的重评估，而非默认继续。

**依据二 · 双库会破坏一条不可权衡的约束**（更关键）

原方案中有一句：「Fund Score、Universe 快照 → 明细入 CK，快照元信息入 PG」。这意味着**同一个快照被拆在两个库里**。

而上游 §8.4 规定：

> 决策快照必须处于**同一个一致性边界**内，能够在**单一事务**中完整写入。

跨库写入没有单一事务保证。要维持"全有或全无"语义，需要引入分布式事务或补偿机制——**这份复杂度直接威胁 `NFR-REPRO-001`（可复现）与 `NFR-AUDIT-001`（可追溯）两项 P0 质量属性**。

> 为了一个当前用不上的性能优势，引入直接损害核心质量属性的复杂度——这不是划算的交易。

**依据三 · 运维成本**

少一套存储意味着：少一套备份恢复流程、少一套监控、少一种查询方言、少一类故障模式、少一份团队学习成本。第一阶段的复杂度预算应投入策略正确性。

### 4.3 一致性边界在单库下的落地

| 快照 | 一致性要求 | 单库实现 |
|---|---|---|
| Decision Snapshot | 全有或全无 | 单一事务内写入全部组成部分 |
| Universe Snapshot | 全有或全无 | 同上 |
| Peer Group Snapshot | 成员与分类版本同边界 | 同上 |

> 在单库下，这三条从"需要额外机制保证"变成"**天然成立**"。这是本次选型最大的收益，超过性能考量。

### 4.4 重评估触发条件

出现以下任一情况时，必须重新评估是否引入列存 / 时序数据库：

| 触发条件 | 原因 |
|---|---|
| 因子数量从 ~50 增至 **500+** | 明细行数进入十亿级 |
| 引入**分钟级或 tick 级**数据 | 频率跃升三个数量级 |
| 引入 **ML 特征工程**（Phase 3） | 派生特征通常爆炸式增长 |
| 需支撑**大量并发的即席聚合分析** | 关系型数据库的 OLAP 短板 |
| 单表超 **10 亿行**且分区后仍不达标 | 进入列存的实际收益区 |

> 届时的引入方式应为**旁路只读副本**（分析型查询走列存，权威写入仍在关系型），而非把快照拆到两个库——一致性约束在任何阶段都不可放弃。

### 4.6 关键负载与性能验证要求

> **选型结论必须由负载验证支撑，而非由数据量推断。** 下表定义必须实测的负载模式。

#### 4.6.1 Workload Matrix

| # | 负载 | 访问模式 | 数据量级 | 频率 | 延迟要求 | 风险 |
|---|---|---|---|---|---|---|
| W1 | 单基金单因子时间序列 | 点查 + 范围扫描 | 千级行 | 高频（交互） | 交互级 | 低——索引友好 |
| W2 | **单时点全市场因子横截面** | **宽表扫描** | 1.2 万 × 50 因子 | 每决策时点 | 批量级 | **中——列存优势场景** |
| W3 | Peer Group 内分位排名 | 分组聚合 + 排序 | 千级 × 数十指标 | 每决策时点 | 批量级 | 中 |
| W4 | **每日因子批量写入** | 批量插入 | 60 万行/日 | 每日 | 批量级 | 中——需关注写放大与 vacuum |
| W5 | 决策快照写入 | **单事务多表写入** | 单次数千行 | 每决策时点 | 批量级 | **高——一致性边界所在** |
| W6 | 历史决策重建 | 多表关联 + 版本解析 | 单次 | 低频 | 可秒级 | 低 |
| W7 | **回测逐期读取** | 时点视图重复扫描 | 数十~数百期 × W2 | 回测时高频 | 吞吐优先 | **高——回测总耗时的主要来源** |
| W8 | Universe / Peer Group 快照读写 | 批量读写 | 千级行 | 每决策时点 | 批量级 | 低 |

#### 4.6.2 验证门槛

以下为**选型成立的前提条件**，须在 Test 环境以结构完整的历史数据实测：

| 验证项 | 判据 | 核心指标 | 未通过时 |
|---|---|---|---|
| **W2 横截面扫描** | **P95 latency < X** | P95 | 优先尝试分区/索引/物化优化；仍不达标则触发 §4.4 重评估 |
| **W5 决策快照事务** | 单事务完整写入且 **P95 latency < Y** | P95 | **不可通过放弃一致性来解决**——见 §4.3 |
| **W7 回测吞吐** | 单次标准回测**总耗时 < Z**，且随「基金数 × 期数」**近似线性** | 总耗时 + 线性度 | 评估结果缓存或只读副本；超线性恶化须定位原因 |
| **W4 写入吞吐** | 每日批量在时间窗内完成 | 时间窗 | 调整批大小与分区策略 |
| **资源余量** | **CPU < 70%** 且 **Memory < 75%** | 峰值占用 | 达标但资源打满不算通过——见 §4.6.2.1 |

**完整验收条件**：

```
PostgreSQL Architecture ACCEPTED
    IF  W2 P95   < X
    AND W5 P95   < Y
    AND W7 total < Z
    AND W7 随「基金数 × 期数」近似线性
    AND CPU    < 70%
    AND Memory < 75%
```

##### 4.6.2.1 为什么资源余量是独立的验收项

> **「延迟达标但 CPU 打到 95%」不是通过。**

延迟指标回答「现在够不够快」，资源余量回答「还能不能扛得住增长」。一个在 95% CPU 下勉强达标的系统，数据量增长 20% 就会跌出 SLO，而那时已无优化空间可用 —— 此刻的「通过」把重评估推迟到了最坏的时机。

> **两条门槛的方向不同**：延迟是当下的**功能性**要求，资源余量是未来的**可持续性**要求。只验前者会让选型结论在半年后失效。

##### 4.6.2.2 指标用 P95 而非平均值

| 指标 | 问题 |
|---|---|
| 平均值 | 被大量快查询稀释，掩盖尾部 |
| **P95**（已采纳） | 反映多数使用者实际感受到的最慢情形 |
| P99 | 在本场景样本量下噪声过大，单次 GC 或 checkpoint 即可主导 |

> **W7 用总耗时而非 P95** —— 它是一次长任务而非请求流，「95% 的期读得快」对一次 8 小时的回测没有意义，使用方关心的是何时能拿到结果。

##### 4.6.2.3 未达标时的升级路径

```
Benchmark Failed
      ↓
① 优先尝试分区 / 索引 / 物化优化
      ↓ 仍不达标
② 评估列存旁路（只读副本）
      ↓
ClickHouse / DuckDB / 其他
```

> **列存若被引入，形态必须是旁路只读副本，不是把快照拆到两个库** —— 一致性约束在任何阶段都不可放弃（§4.4）。这与「不引入 ClickHouse」的原决策不矛盾：原决策的理由是双库破坏「决策快照单一事务」约束，而**只读副本不承担写入**，不触碰该约束。

> **W5 的特殊性**：它是唯一**不能靠性能优化让步**的负载。若单事务写入成为瓶颈，正确的解法是优化快照结构或存储配置，**不是**把快照拆到多个事务——那会破坏上游 §8.4 的约束（`01-system-architecture` C-4）。

#### 4.6.3 验证的时机

| 时机 | 内容 |
|---|---|
| **选型确认前** | W2、W5、W7 三项必须完成基准测试 |
| 每次 Major 策略版本变更 | 重跑 W7（回测负载可能显著变化） |
| 数据规模翻倍时 | 全量重跑 |

> **`TBD-TECH-7` 的性质已于 2026-08-27 变更**：验收**框架**已定案（指标口径 P95、资源余量门槛、完整验收条件、升级路径），剩余的只是三个数值 X / Y / Z —— 它们必须由压测产出，不能由文档指定。见 `TBD-resolution.md` Policy ⑦。

## 5. Quantitative Computing 与 Backend

### 5.0 三个层次的分离

> **虽然三者都用 Python，但它们是不同的层次，职责、依赖方向与版本管理均不同。混为一谈会让"策略逻辑"混入服务代码，破坏可复现性。**

```
┌──────────────────────────────────────────────┐
│  Backend Service Layer                       │  API 承载 · 用例编排 · 权限 · 任务提交
│  依赖 ↓                                       │  不含任何投资策略规则
├──────────────────────────────────────────────┤
│  Strategy Library（SDL 的技术实现）            │  Factor · Peer Group · Score · Universe
│  依赖 ↓                                       │  Return Estimation · Risk · Construction · Optimization
├──────────────────────────────────────────────┤
│  Quant Engine                                │  数值计算基础：矩阵 · 统计 · 优化求解
│                                              │  不含任何业务语义
└──────────────────────────────────────────────┘
```

| 层 | 内容 | 版本管理 | 关键约束 |
|---|---|---|---|
| **Backend Service** | API 承载、编排、权限、任务提交、数据访问实现 | 常规发布版本 | **不得包含投资策略规则** |
| **Strategy Library** | 全部领域策略逻辑，实现 Strategy Execution Interface | **纳入 Code Version（§5.4），影响结果** | 不含数据访问实现；不感知 runtime_mode |
| **Quant Engine** | NumPy / pandas / SciPy + 优化求解器 | **纳入 Code Version**，版本必须锁定 | 不含业务语义 |

**依赖方向单向**：Backend → Strategy Library → Quant Engine。反向依赖（如 Quant Engine 引用业务概念）视为设计错误。

> **为什么 Strategy Library 必须独立于 Backend**：它是 Live 与 Backtest 共用的那一套逻辑（§9）。若与 Backend 服务代码混在一起，回测复用就退化为"调用实时服务"，破坏 PIT 与历史时钟。

### 5.1 选型：Quant Engine —— Python 科学计算栈

| 字段 | 内容 |
|---|---|
| **Technology** | Python + NumPy / pandas / SciPy |
| **Purpose** | 数值计算基础层：矩阵运算（协方差、相关性）、统计分析、时序处理 |
| **Why Selected** | ① 量化金融领域的**事实标准**，生态成熟<br/>② 矩阵与时序运算的表达力直接对应业务语义，代码可读性高（P-1）<br/>③ 统计与优化库齐全，无需自行实现数值算法<br/>④ 便于投研人员参与验证——策略逻辑可被非工程人员审阅 |
| **Alternative** | Java / Scala（JVM 生态）；R；C++ |
| **Trade-offs** | 单线程性能低于编译型语言；需注意向量化以避免 Python 层循环；GIL 限制多线程并行（可用多进程绕过） |
| **Current Phase** | Quant Engine 与 Strategy Library 的实现语言 |
| **Future Consideration** | 性能瓶颈处可用编译型扩展补充，无需更换主语言 |

> **Backend Service Layer 的语言选择**：第一阶段同样采用 Python，理由是避免 Strategy Library 跨语言调用的额外复杂度。但这是**可替换的决定**——若未来 Backend 与 Strategy Library 分离部署，Backend 可采用其他语言，只要通过 Strategy Execution Interface 交互。

### 5.2 选型：凸优化求解器

| 字段 | 内容 |
|---|---|
| **Technology** | 凸优化建模层 + 开源求解器（如 CVXPY 配合 OSQP / Clarabel / ECOS） |
| **Purpose** | Portfolio Optimization——在约束集下求解目标权重 |
| **Why Selected** | ① 第一阶段的优化目标经适当变换后**均可归约为凸问题**（QP 或 LP，见 §5.2.1），开源求解器胜任<br/>② 建模层让约束以接近数学表达的形式书写，**可解释性强**（P-1）<br/>③ **求解器版本可固定**——这是 `NFR-REPRO-001` 的必要条件<br/>④ 求解状态（可行 / 不可行 / 收敛）由求解器显式返回，天然支持 `INFEASIBLE` 的业务语义 |
| **Alternative** | 商业求解器（Gurobi / MOSEK）；自行实现数值优化 |
| **Trade-offs** | 大规模问题的求解速度不及商业求解器；**引入基数约束或最小持仓量约束时问题变为混合整数（非凸），开源 MIQP 能力有限** |
| **Current Phase** | 第一阶段使用开源求解器 |
| **Future Consideration** | Universe 规模显著增大、或引入 §5.2.2 所列的非凸约束时，评估商业求解器 |

#### 5.2.1 各优化目标的数学性质

> **此前版本笼统称"第一阶段目标均为凸问题"，该表述不准确。** 各目标的性质与求解路径如下：

| 优化目标 | 数学性质 | 求解路径 | 第一阶段 |
|---|---|---|---|
| **Equal Weight** | 无优化问题 | 确定性映射 + 约束投影 | ✅ |
| **Score Weight** | 无优化问题 | 确定性映射 + 约束投影 | ✅ |
| **Minimum Volatility** | **凸 QP** | 直接求解 `min w'Σw` | ✅ |
| **Maximum Sharpe** | **拟凸**（分式规划） | **需 Charnes-Cooper 变换**转为凸 QP——见下方前提 | ✅ |
| Risk Parity | 凸（对数障碍形式） | 转为凸问题求解 | 后续 |
| **Minimum CVaR** | **凸 LP** | Rockafellar-Uryasev 表达：引入辅助变量后为线性规划 | 后续 |

##### Maximum Sharpe 的变换前提（必须在 `06-portfolio` 落实）

Maximum Sharpe 的原始形式是分式目标：

```
max  (μ − r_f·1)'w / sqrt(w'Σw)
```

它**不是凸问题**，但在约束集**可齐次化**时，可通过 Charnes-Cooper 变换（令 `y = κw`，`κ > 0`）转为凸 QP：

```
min  y'Σy
s.t. (μ − r_f·1)'y = 1
     其余约束齐次化为 y 与 κ 的线性约束
```

| 约束类型 | 变换是否成立 |
|---|---|
| 权重上下限 `w_i ≤ u`、`sum(w) = 1` | ✅ 齐次化为 `y_i ≤ u·κ`、`sum(y) = κ` |
| 类别权重上限 | ✅ 同上 |
| **换手率约束** `‖w − w_prev‖ ≤ T` | ❌ **不成立**——`w_prev` 是常量，破坏齐次性 |
| **最小持仓量**（`w_i = 0` 或 `w_i ≥ l`） | ❌ 本身即非凸 |

> **架构含义**：当策略同时启用 Maximum Sharpe 与换手率约束时，Charnes-Cooper 路径不可用，须改用**风险厌恶参数扫描**（对 `λ` 求解一族 `max μ'w − λ/2·w'Σw` 后取 Sharpe 最优）或直接的拟凸求解方法。具体方法由 `docs/06-portfolio` 定义；本层的要求是：**求解路径必须随 `Portfolio Rule Version` 显式声明**，不得由实现隐式选择——否则相同配置在不同实现下会得到不同结果。

##### 5.2.2 真正的非凸情形

以下约束会使问题变为**混合整数**（非凸），开源求解器能力有限：

| 约束 | 说明 |
|---|---|
| **基数约束** | "最多持有 N 只基金" |
| **最小持仓量** | `w_i = 0` 或 `w_i ≥ l`（避免碎片持仓） |
| **最小交易量** | 单笔调整为 0 或不低于某阈值 |

> 第一阶段的 Minimum Trade Threshold（`FR-REBAL-002`）以**事后过滤**方式实现（求解后剔除小额调整），而非作为优化约束——这避免了引入混合整数问题。若未来需要将其作为硬约束进入优化，须重新评估求解器。

> **可复现性要求**：求解器版本必须固定并记入 `Portfolio Rule Version`。求解器升级可能改变数值结果，属于影响输出的配置变更（`NFR-REPRO-001` REPRO-1）。

### 5.3 任务编排：三个必须分开的概念

> **`Scheduler`、`Task Queue`、`Message Broker` 是三种不同的能力，此前版本将其混用。** 某些产品同时提供多项，但**能力需求必须分开论证**，否则会因"某产品能做"而引入实际不需要的能力。

| 能力 | 解决什么 | 本系统是否需要 |
|---|---|---|
| **Scheduler** | **何时触发**、**按什么顺序** | ✅ **必需** |
| **Task Queue** | **谁来执行**、如何分发给 Worker | ✅ **必需** |
| **Message Broker** | **谁需要知道**——事件的发布订阅 | ❌ 第一阶段不需要（§6.2） |

#### 5.3.1 Scheduler（触发与编排）

| 字段 | 内容 |
|---|---|
| **Purpose** | 决策日链路的**顺序编排**、周期性批量计算的定时触发 |
| **能力要求** | ① **DAG 依赖保证**——链路各阶段有严格前后依赖（如 Post-Opt Risk 必须在 Optimization 之后）<br/>② 触发条件可配置（周期、依赖满足）<br/>③ 任务状态持久化，调度器重启后可续跑<br/>④ 部分失败可见——定位到具体节点而非整批 |
| **Alternative** | 纯 cron + 脚本（**不满足 DAG 依赖与状态持久化**）；自研 |
| **Trade-offs** | 引入需独立运维的组件；但决策链路的顺序依赖使 cron 方案的隐性成本更高 |
| **选型** | `<TBD-TECH-1>` |

> **约束**：Scheduler 只负责**编排与触发**，**不得承载业务判断**。"在调度配置里写 if 条件"会让策略规则逃离版本化范围，破坏可复现性（§12 D-8）。

#### 5.3.2 Task Queue（分发与执行）

| 字段 | 内容 |
|---|---|
| **Purpose** | 将计算任务分发给 Worker 池；承载回测这类长时异步任务 |
| **能力要求** | ① **幂等键支持**——重复投递不产生重复结果（`04-integration-architecture` §4.4）<br/>② 任务状态与进度可查询（长时回测必需）<br/>③ 失败重试策略可按任务类型区分（`INFEASIBLE` 不重试）<br/>④ Worker 池可按队列分池——回测与批量计算优先级不同（`05-deployment-architecture` RT-2） |
| **Alternative** | 由 Scheduler 直接执行（**不满足 Worker 池分池与长时任务进度**）；数据库轮询 |
| **Trade-offs** | 与 Scheduler 可能是同一产品也可能是两个组件，取决于选型 |
| **选型** | `<TBD-TECH-1>`——**可与 Scheduler 同产品，但能力需求须分别验证** |

#### 5.3.3 为什么 Message Broker 不在此列

Scheduler 与 Task Queue 解决的是**已知的、有明确依赖顺序的**工作分发；Message Broker 解决的是**事件的多方订阅**。本系统第一阶段没有多消费者事件场景——详见 §6.2。

> **常见误判**：因为选定的调度产品"自带消息队列"就顺手引入事件驱动。这会把有严格顺序依赖的链路改造成依赖投递语义的事件流，是可靠性的倒退（`04-integration-architecture` D-1）。

### 5.4 Code Version：可复现性的第四个要素

> **`01-system-architecture` §8 定义了 Data Version + Strategy Version + Execution Context 三要素。本节补充第四个：Code Version。**

**问题**：九项 Strategy Version 记录的是**规则与配置**。但相同配置在不同代码版本下可能产出不同结果——策略库的实现变更、求解器版本升级、数值库的 BLAS 后端差异，都会改变数值输出。

**因此可复现性的完整公式为**：

```
Data Version  +  Strategy Version（九项）  +  Code Version  +  Execution Context
                            ↓
                    完全相同的结果（在既定容差内）
```

#### 5.4.1 Code Version 的组成

| # | 组成 | 为什么影响结果 |
|---|---|---|
| 1 | **Strategy Library Version** | 领域逻辑的实现变更直接改变计算结果 |
| 2 | **Optimization Solver Version** | 求解器算法与收敛判据变化会改变权重解 |
| 3 | **Quant Engine Version**（NumPy / SciPy 及其 BLAS 后端） | 数值库实现差异导致浮点结果的微小偏移 |

#### 5.4.2 强制要求

| # | 要求 |
|---|---|
| CV-1 | 上述三项版本必须**显式记录于决策快照**，而非作为隐含依赖 |
| CV-2 | Strategy Library 的版本变更视为**影响输出的变更**，须触发可复现性回归（§8.2） |
| CV-3 | 求解器与数值库版本必须**锁定**，升级须走与策略变更相同的验证流程 |
| CV-4 | CI 强制校验各服务与 Worker 依赖的 Strategy Library 版本**一致** |

> 此前版本称"库版本纳入 Strategy Version 的隐含依赖"——**"隐含"是不够的**。隐含依赖无法在快照中查询，也无法在复现时校验。Code Version 必须是快照中的显式字段。

#### 5.4.3 数值容差

> **浮点计算的完全位级一致不是可达目标**，可复现性必须定义容差。

| 对象 | 容差要求 | 说明 |
|---|---|---|
| **Factor 值 / Score** | 相对误差 **1×10⁻¹⁰** | 确定性算术，运算链短，误差不累积 |
| **协方差矩阵** | 相对误差 **1×10⁻⁸** | 受 BLAS 实现与求和顺序影响，N×T 次累加 |
| **优化权重 `w`** | 相对误差 **1×10⁻⁶**，且**排序与非零集合必须一致** | 求解器终止容差通常 1e-8~1e-6，结果精度不会优于终止容差 |
| **绩效指标** | 相对误差 **1×10⁻⁸** | 由上游误差累积，但无迭代放大 |

**判定规则**：

| # | 规则 |
|---|---|
| TOL-1 | 差异在容差内 → 视为**可复现** |
| TOL-2 | 差异超出容差 → 视为**缺陷**，须定位到具体环节 |
| TOL-3 | **权重的非零集合（持有哪些基金）必须完全一致**——这不是数值问题，若不一致说明求解路径分叉 |
| TOL-4 | 容差不得用于掩盖逻辑差异——同一 Code Version 下的重跑应当接近位级一致 |

> **已定案 · 2026-08-27**：上表取值已填入。见 `TBD-resolution-2.md` Policy A。

**为什么权重的容差比因子松四个数量级**：优化器的解是迭代逼近的，其精度上限就是终止容差。要求权重复现到 1e-10，等于要求求解器每次走完全相同的迭代路径 —— 那是对**实现细节**的要求，不是对**结果**的要求。TOL-3（非零集合必须一致）才是权重层真正的硬约束。

**存储精度**（本条此前未覆盖，一并定案）：

| 对象 | 类型 |
|---|---|
| 金额 | `NUMERIC(20,4)` |
| 净值 / 因子值 | `NUMERIC(18,8)` |
| 权重 / 比率 / 利率 | `NUMERIC(12,8)` |

> **容差与精度是两件事**：精度决定「能存多细」，容差决定「差多少算不一致」。两者都定了，可复现性才可判定 —— 只定容差而存储精度不足，会让本可复现的结果因存储截断而超差。

## 6. 第一阶段刻意不引入的技术

> 每一项都回答"不引入它会怎样"。

### 6.1 Cache —— 暂不引入

| 项 | 说明 |
|---|---|
| **不引入的理由** | 系统主要负载是批量计算而非高并发在线查询；在线查询量级小，数据库直接支撑即可 |
| **不引入的代价** | 热点查询（如常用基金的历史指标）每次访问数据库 |
| **何时引入** | 在线查询 P95 延迟不达标（NFR-1），且瓶颈定位在重复读取 |
| **引入时的注意** | 历史数据天然不可变，**缓存失效逻辑简单**；但**当前状态类数据（Live Portfolio）不应缓存**——陈旧的持仓状态会导致错误的漂移判断 |

### 6.2 Message Broker —— 暂不引入

| 项 | 说明 |
|---|---|
| **不引入的理由** | 决策主链路采用**顺序批量**而非事件驱动（`04-integration-architecture` D-1）；异步场景（回测、外部回报）由 **Task Queue**（§5.3.2）承载——注意 Task Queue 与 Message Broker 是**不同能力**，见 §5.3.3 |
| **不引入的代价** | 服务间的解耦程度较低；外部成交回报的处理需要轮询或轻量接收端 |
| **何时引入** | 出现真正需要广播/多消费者的事件场景；或外部回报的实时性要求提高 |
| **风险提示** | **不要为了"微服务化"引入消息中间件**——把有严格顺序依赖的链路改为事件驱动，会让顺序保证依赖于消息投递语义，是可靠性的倒退 |

### 6.3 Orchestration（容器编排）—— 第一阶段可不引入

| 项 | 说明 |
|---|---|
| **不引入的理由** | 服务数量少（5 个领域服务 + 应用层），负载可预测，容量可静态规划（`05-deployment-architecture` D-7） |
| **不引入的代价** | 扩缩容与故障恢复需要更多人工介入；多环境一致性依赖部署脚本 |
| **何时引入** | 服务实例数增长到人工管理成本超过学习与运维成本；或需要自动弹性伸缩 |
| **保留的能力** | **容器化本身仍然需要**——它保证环境一致性与依赖隔离，与是否引入编排系统无关 |

### 6.4 Analytical Database —— 不引入

见 §4.2 完整论证。

### 6.5 ML / AI 相关技术栈 —— 不引入

| 项 | 说明 |
|---|---|
| **不引入的理由** | 上游 §6.2.1 明确排除；第一阶段建立不依赖 ML 的量化基线 |
| **范围** | 不引入模型训练框架、特征存储、模型服务、向量数据库、LLM 相关组件 |
| **何时引入** | Phase 3 及以后，且必须保留一条不依赖 ML 的基线路径作为对照与回退 |
| **架构预留** | `Return Estimate`、`Factor`、`Fund Score`、`Risk Model` 四处保留可替换的估计器接口，但**第一阶段不建立任何 ML 相关的组件、依赖或数据通道** |

| **决策快照、Universe / Peer Group 快照** | 小~中 | 是 | **PostgreSQL**（一致性边界要求，§4.3） |
| **回测逐期快照与结果** | 中 | 是 | **PostgreSQL**（需按策略版本与区间检索） |
| **回测报告（渲染产物）** | 中~大 | 是 | **PostgreSQL 大对象** 或 **对象存储** —— 见下方判据 |
| **计算中间产物**（单次流水线内的矩阵） | 大 | **否** | **进程内存**，不落盘（`05-deployment-architecture` §4.2） |
| **原始数据落地文件**（Raw 层） | 大 | 是 | **对象存储** 或 PostgreSQL 大对象 |

#### 7.3.2 判据

> **是否引入独立对象存储，取决于"需跨实例共享的大体积不可变产物"的实际量级。**

| 情形 | 方案 |
|---|---|
| 报告与 Raw 文件总量在**百 GB 以内** | 暂用 PostgreSQL 大对象，**保留存储抽象接口** |
| 超出该量级，或备份/恢复因大对象显著变慢 | 引入对象存储 |

**无论选哪种，架构要求一致**：

| # | 要求 |
|---|---|
| OS-1 | 通过**存储抽象接口**访问，业务代码不感知底层是数据库大对象还是对象存储 |
| OS-2 | **不使用本地文件系统**作为跨实例共享的存储——Worker 可水平扩展且可被重建 |
| OS-3 | 大体积产物的引用（而非内容）随快照落库，保证可追溯 |

`<TBD-TECH-4: 报告与 Raw 文件的实际量级待评估，据此决定是否引入独立对象存储>`

## 9. Strategy Domain Logic 的技术承载

> 这是 `01-system-architecture` ARCH-1 与 `02-service-architecture` SVC-1 遗留的问题。

### 9.1 需求

`Backtest` 与 `Live` 必须共用同一套 Strategy Domain Logic，差异仅限数据源与时间轴（上游 §5.4）。

其**逻辑接口边界**已由 `01-system-architecture` §11.2 定义为 **Strategy Execution Interface**：

```
Input:  Decision Execution Context + PIT Data Context
        + Strategy Version（九项）+ Recompute Scope
Output: Decision Snapshot（闭包）
```

本节确定该接口的**技术承载形态**。

### 9.2 两种承载形态

| 形态 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A · 共享库** | 策略逻辑封装为内部库，各服务与回测 Worker 依赖同一版本 | 无跨进程开销；矩阵等大对象直接传递 | 各服务需同步升级库版本 |
| **B · 共享服务** | 策略逻辑作为服务，回测通过调用复用 | 版本天然统一 | 大体积中间产物跨进程传输；回测的高频调用产生大量网络开销 |

### 9.3 第一阶段选择：形态 A（共享库）

| 理由 | 说明 |
|---|---|
| ① 大对象传递 | 协方差矩阵在回测中每期产生，跨进程传输代价高而收益为零 |
| ② 调用频次 | 一次回测触发数十至数百轮完整链路，跨进程开销被放大 |
| ③ 与服务边界不冲突 | 领域服务仍然是独立部署单元，只是共享同一个策略逻辑库 |
| ④ 版本一致性可控 | 库版本纳入 `Strategy Version` 的隐含依赖，CI 强制各服务版本对齐 |

**约束**：

| # | 约束 |
|---|---|
| SDL-1 | 策略逻辑库**不得包含**数据访问实现——数据访问通过注入的接口提供 |
| SDL-2 | 库内**不得出现**任何"是否回测"的判断分支 |
| SDL-3 | 库版本变更视为影响输出的变更，须纳入版本管理与可复现性回归 |

## 11. Summary

第一阶段技术栈的核心是**克制**：

- **单一 PostgreSQL 承载全部持久化** —— 不是因为它性能最强，而是因为它让"决策快照单一事务写入"这条不可权衡的约束天然成立，且当前数据规模远未进入列存的收益区间
- **Python 科学计算栈 + 开源凸优化求解器** —— 量化领域的事实标准；第一阶段目标经适当变换后可归约为凸 QP/LP，求解器版本可固定以保证可复现
- **Strategy Domain Logic 采用共享库** —— 避免大体积中间产物跨进程传输，同时保持服务的独立部署
- **刻意不引入 Cache、Message Broker、容器编排、分析型数据库** —— 每一项都给出了"不引入的代价"与"何时引入"，而非无限期搁置

> 每一个未引入的组件都是**被论证过的决定**，不是遗漏。

**两点必须强调**：

1. **L1 基线尚待一项验证**——`OPEN-14`（W2/W5/W7 的 SLO 数值，原 TECH-7）是基线**成立的前提**。在压测完成前，「单库 PostgreSQL 已定案」应理解为**待验证的选择**（§14.3）。**TECH-8（数值容差）已于 2026-08-27 定案**（§5.4.3），不再是前提。
2. **可复现性有四个要素而非三个**——`Data Version + Strategy Version + Code Version + Execution Context`。`Code Version`（策略库、求解器、数值库）此前被当作隐含依赖，现已显式化（§5.4）。

## 12. Decisions

| # | 决策 | 关键理由 |
|---|---|---|
| D-1 | **单一 PostgreSQL，不引入 ClickHouse** | 一致性约束（决策快照单一事务）比性能更硬；数据规模十亿行以内，未进入列存收益区 |
| D-2 | 未来引入列存时采用**旁路只读副本**形态 | 一致性约束在任何阶段都不可放弃，不得把快照拆到两个库 |
| D-3 | Python 作为后端与量化计算的统一语言 | 避免策略逻辑跨语言实现两次；便于投研人员参与验证 |
| D-4 | 使用开源凸优化求解器，版本固定并纳入 Portfolio Rule Version | 第一阶段目标经变换后均可归约为凸 QP/LP（§5.2.1）；版本固定是可复现的必要条件 |
| D-5 | Strategy Domain Logic 采用**共享库**而非共享服务 | 回测每期传递大体积矩阵，跨进程开销被数百轮调用放大 |
| D-6 | 不引入 Cache / Message Broker / 容器编排 | 各自给出了不引入的代价与引入触发条件；第一阶段复杂度预算投入策略正确性 |
| D-7 | CI 强制执行可复现性回归 | 一般系统 CI 验证功能正确，本系统还须验证结果与历史一致 |
| D-8 | 调度器只负责编排，不承载业务逻辑 | 调度配置中的判断条件会逃离版本化范围，破坏可复现性 |
| D-9 | **Quant Engine / Strategy Library / Backend Service 三层分离** | Strategy Library 是 Live 与 Backtest 共用的那一套；与 Backend 混合会使回测复用退化为"调用实时服务" |
| D-10 | **引入 Code Version 作为可复现性第四要素** | 九项 Strategy Version 只记录规则与配置；代码、求解器、数值库版本同样改变结果 |
| D-11 | **Scheduler 与 Task Queue 作为两种能力分别论证** | 二者解决不同问题；混为一谈会因"某产品能做"而引入不需要的事件驱动能力 |
| D-12 | **不使用本地文件系统作为跨实例共享存储** | Worker 可水平扩展且可被重建，本地文件不共享也不持久 |
| D-13 | **Minimum Trade Threshold 以事后过滤实现，不作为优化约束** | 作为约束会引入最小持仓量的混合整数问题（非凸），开源求解器能力有限（§5.2.2） |
| D-14 | **Maximum Sharpe 的求解路径必须随 Portfolio Rule Version 显式声明** | Charnes-Cooper 变换在存在换手率约束时不成立；路径由实现隐式选择会使相同配置产出不同结果 |
