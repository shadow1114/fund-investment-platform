## 1. 文档目的与边界

### 1.1 本文档回答什么

> **组合在构建、优化与再平衡中必须满足哪些规则？**

### 1.2 约束在三个环节都要满足

```
Construction  →  约束进入问题定义
Optimization  →  约束作为求解条件
Rebalancing   →  调仓后必须继续满足
```

> **约束不是只在优化时校验一次的东西** —— 净值漂移会使已满足的约束重新被违反（见 §9）。

### 1.3 本文档不回答什么

| 不回答 | 归属 |
|---|---|
| 风险如何**分配** | `04-risk-budgeting` |
| 类别配置的**目标** | `02-asset-allocation` |
| 求解与不可行处理 | `03-portfolio-optimization` |
| 调仓触发与换手判据 | `06-rebalancing` |
| 基金准入规则（Eligibility Rules） | `05-fund-evaluation/05` |

### 1.4 Constraint 与 Eligibility Rules 的区别 ⚠️

> **两者都是"限制"，但作用对象完全不同。**

| | **Eligibility Rules** | **Portfolio Constraint** |
|---|---|---|
| 作用对象 | **单只基金**能否进入候选池 | **组合整体**的权重结构 |
| 归属 | `05-fund-evaluation/05` | 本文档 |
| 判定时机 | 构建 Universe 时 | 优化求解时 + 持续监控 |
| 典型 | "成立满 3 年" | "单基金权重 ≤ X%" |
| Strategy Version 项 | 第 3 项 `Eligibility / Universe Version` | 第 7 项 `Portfolio Rule Version` |

## 2. Constraint Scope：约束必须声明作用对象 ⚠️

> **这是约束定义中最容易出错的一处。**

```
❌ "Maximum Weight = 10%"
   → 10% applies to what?
   → 单只基金？某个类别？前 N 大合计？
```

### 2.1 五种作用域

| Scope | 含义 | 示例 |
|---|---|---|
| **`PORTFOLIO`** | 整个组合 | 组合波动率 ≤ X% |
| **`ASSET_CLASS`** | 某个资产类别 | Equity ∈ [X%, X%] |
| **`FUND`** | 单只基金 | 单基金权重 ≤ X% |
| **`GROUP`** | 一组基金（如同一管理人） | 同一管理人合计 ≤ X% |
| **`RISK_FACTOR`** | 风险因子暴露 | 某因子暴露 ≤ X |

### 2.2 每条约束必须完整声明五项

| 项 | 说明 |
|---|---|
| **`constraint_type`** | 约束类型 |
| **`scope`** | 作用域（§2.1） |
| **`scope_key`** | 作用域的具体对象（如 `asset_class = Equity`） |
| **`min` / `max`** | 上下限 |
| **`hard_or_soft`** | 硬约束或软约束（§4） |

> 缺 `scope` 或 `scope_key` 的约束**不得进入约束集** —— 它无法被校验，也无法被解释。

### 2.3 `GROUP` 作用域需要分组依据

> `GROUP` 是唯一需要外部数据支撑的作用域。

| 分组依据 | 数据来源 | 第一阶段 |
|---|---|---|
| 同一 **基金管理人** | `03-data`（`Fund Management Company`） | ✅ 可用 |
| 同一 **基金经理** | `03-data`（`Fund Manager Tenure`，PIT） | ✅ 可用 |
| 同一 **基金**的多份额 | `03-data`（Share Class 关系） | ✅ 可用 |
| 同一 **策略** | **无数据支撑** | ❌ |

> **同一管理人集中度是一个真实的风险** —— 单一管理人出现运营或合规问题时，其旗下多只基金会同时受影响，而这类相关性不体现在净值协方差中。

> **推荐默认 · 2026-08-27**：**启用管理人集中度约束**，单一管理人上限 **30%**；**不启用基金经理层约束**。风控可改。
>
> **依据 —— 两层的数据可得性不同**：
>
> | 层 | 是否启用 | 理由 |
> |---|---|---|
> | **管理人（基金公司）** | ✅ 启用 | 真实的运营风险集中 —— 同一公司的合规问题、投研体系变动会同时影响其全部产品；且管理人归属数据稳定完整 |
> | 基金经理 | ❌ 不启用 | **历史完整性不足**（同 `08-backtest/04` `SB-3` 对 Eligibility 历史的判断）—— 经理变更、共管、挂名的历史记录质量参差，据此设约束会产生大量误判 |
>
> **30% 的量级依据**：三家管理人可覆盖组合全部，是分散化的最低要求。该值属可调参数。
>
> **基金经理层的风险仍须监控** —— 通过 `P1-9` 的 Manager Change 观察期机制，而非通过持仓约束。

## 3. Constraint Categories

### 3.1 分类与可行性

| 类别 | 约束 | 事前可约束 | 第一阶段 |
|---|---|:---:|---|
| **权重** | 单基金上下限 | ✅ | ✅ |
| | 非负（不做空） | ✅ | ✅ **必需** |
| | 权重和为 100% | ✅ | ✅ **必需** |
| **资产配置** | 类别上下限 | ✅ | ✅ |
| **集中度** | 前 N 大权重合计上限 | ✅ | ✅ |
| | 权重 HHI 上限 | ✅ | 见 §3.2 |
| **风险** | 组合波动率上限 | ✅ | ✅ |
| | Tracking Error 上限 | ✅ | 需 Portfolio Benchmark |
| | VaR / CVaR 上限 | ✅ | 需组合层计算（`04` §2.1） |
| | **最大回撤上限** | **❌** | **见 §3.3** |
| | 风险贡献占比上限 | ✅ | 属 `04-risk-budgeting` |
| **换手** | 换手率上限 | ✅ | ✅（仅 `REBALANCE` 模式） |
| | 单笔最小交易量 | ❌ 非凸 | 见 `06-rebalancing` |
| **流动性** | 基金规模下限 | ✅ | 属 Eligibility Rules |
| **运营** | `Investment Eligibility` 状态 | ✅ | ✅ **必需** |
| **基数** | 最多持有 N 只 | ❌ 非凸 | 通过 Universe 层规避（`01` §12.2） |

### 3.2 HHI 约束是凸的，但需注意形式

> **权重的 Herfindahl 指数 `HHI = Σ w_i²` 是凸函数**，因此 `HHI ≤ c` 是凸约束（可作为二次约束）。

但需注意：

```
HHI ≤ c  等价于  ||w||₂² ≤ c
    → 这是一个二次约束，使问题从 QP 变为 QCQP
    → 仍是凸的，但求解器需支持二次约束
```

> **"前 N 大权重合计 ≤ X%" 则是线性约束**，实现更简单，且业务含义更直观。第一阶段**优先使用前 N 大形式**。

### 3.3 最大回撤不能作为事前约束

> **沿用 `02-business-requirements` §20.2 与 `04-risk-budgeting` §3。**

```
Future MaxDD(w) ≤ X   ❌ 依赖未来价格路径，建仓时未知
```

最大回撤**默认为事后监控指标**。若需事前控制，必须先定义可计算的代理（历史情景重演 / 蒙特卡洛路径分位 / 波动率代理），并承认其局限。

> **不得把一个无法计算的量写入约束集** —— 那会让优化器面对一个无法表达的要求。

## 4. Hard vs Soft Constraints

### 4.1 定义

| | **Hard Constraint** | **Soft Constraint** |
|---|---|---|
| 语义 | **必须满足** | 允许违反，但产生惩罚 / 告警 |
| 在优化问题中 | 约束条件 | **目标函数中的惩罚项** |
| 违反的后果 | `INFEASIBLE` | 目标函数值变差 |

### 4.2 第一阶段只实现 Hard Constraints

> **理由不是"简单"，而是 Soft Constraint 会引入一个未定义的权衡。**

```
Soft Constraint 需要一个惩罚系数 λ_penalty
    → λ 的取值决定"违反多少约束换取多少目标改善是划算的"
    → 这是一个投资决策，不是技术参数
    → 且 λ 会改变最优解，必须纳入 Portfolio Rule Version
```

**在没有业务依据确定 `λ` 之前，引入 Soft Constraint 等于让实现者替业务做决策。**

> **已定案 · 2026-08-27**：第一阶段**不引入 Soft Constraint**。
>
> **依据**：软约束需要惩罚系数，而**惩罚系数是又一组无依据的参数** —— 它的量纲要与目标函数可比（如「超限 1% 相当于损失多少收益」），而这个换算本身就是一个未经论证的风险偏好表达。
>
> **硬约束 + `INFEASIBLE` 反馈更透明**（同 `PO-4`）：约束要么满足要么不满足，不可行时暴露冲突集由人决策。软约束会让「违反了多少」变成一个隐藏在目标函数里的连续量。
>
> **唯一的例外是 `VIOLATED_BY_FROZEN`**（`CS-5`）—— 那不是「软化的约束」，而是「因外部不可交易而无法满足的硬约束」，其处理是标记与留痕，不是加惩罚项。

### 4.3 硬约束不得被静默违反

> **沿用 `03-portfolio-optimization` §8.2：**

```
❌ 求解器发现无解 → 放松硬约束 → 返回"差不多的解"
✅ 返回 INFEASIBLE → 上报 → Construction 层显式决策
```

## 5. Constraint Priority

### 5.1 优先级用于冲突处理

> **当多个约束冲突导致 `INFEASIBLE` 时，优先级决定"先考虑放松哪一条"。**

```
Constraint Priority = TBD
```

> **本参数当前为 TBD，投产前必须由业务负责人确认。**

参考的分层思路（**非本域拍板**）：

```
Regulatory  >  Business  >  Risk  >  Optimization Preference
```

> **已定案 · 2026-08-27**：约束优先级 = **合规 > 风控 > 投资策略 > 成本**。
>
> | 层 | 典型约束 | 可协商性 |
> |---|---|---|
> | **合规** | 单一基金持有比例上限、禁投名单 | **不可协商** —— 违反是合规事件 |
> | **风控** | Risk Budget、集中度上限、CVaR 上限 | 须风控审批 |
> | **投资策略** | 资产类别目标权重、持仓数范围 | 投研可调 |
> | **成本** | 换手率上限、最小交易金额 | 可权衡 —— 成本本就是与收益权衡的对象 |
>
> **本序列在第一阶段用于人工决策的参考，不用于自动松弛**（`PO-4`）。它的作用是在 `INFEASIBLE` 时告诉人「应该先考虑放松哪一层」。
>
> **成本排在最后不代表不重要** —— 而是它与其它三层的性质不同：前三层是**边界**（越过即错误），成本是**权衡项**（多花一点换更好的组合可能是划算的）。

### 5.2 优先级不等于自动放松许可 ⚠️

> **这是一处必须澄清的地方。**

```
优先级回答："如果人决定要放松，应该先放松哪一条"
优先级不回答："系统可以自动放松"
```

第一阶段 `Constraint Relaxation = OFF`（`03` §8.5），因此**优先级仅用于向 Human Review 提供建议顺序**，不构成自动执行的依据。

### 5.3 合规约束不可放松

> 无论优先级如何配置，标记为 `REGULATORY` 的约束**不进入放松候选**。放松合规约束不是一个投资决策，而是一个合规事件。

## 6. Constraint Validation

### 6.1 校验结果的四元组

> **每条约束的校验必须能回答四个问题：**

| 项 | 说明 |
|---|---|
| **Constraint** | 哪条约束（含 scope 与 scope_key） |
| **Expected** | 限制值 |
| **Actual** | 实际值 |
| **Status** | 见 §6.2 |

```
Maximum Fund Weight (scope=FUND, key=Fund A)
  Limit  = TBD
  Actual = X%
  Status = PASS
```

### 6.2 状态

| 状态 | 含义 | 可放行 |
|---|---|---|
| **`PASS`** | 满足 | ✅ |
| **`WARNING`** | 接近限制（在预警带内） | ✅ 须标记 |
| **`BREACH`** | 违反 | ❌ |
| **`NOT_AVAILABLE`** | **无法校验**（所需数据不可得） | ❌ **见 §6.3** |

### 6.3 `NOT_AVAILABLE` 不得当作 `PASS` ⚠️

> 与 `04-risk-budgeting` §7.3 是同一条原则。

```
❌ 组合波动率算不出来（Σ 不可得）→ 视为"没有违反波动率上限" → 放行
   → 把"不知道"当作"没问题"
```

**处理**：`NOT_AVAILABLE` 必须**阻断**并告警。

### 6.4 全部约束必须校验，不得短路

> 与 `05-fund-evaluation/05` §14.4 是同一条原则：遇到第一个 `BREACH` 就返回，会丢失"还违反了哪些"的信息，使排查与放松决策失去依据。

### 6.5 `WARNING` 需要一个预警带定义

> `WARNING` 不是自动产生的 —— 它需要一个"距离限制多近算接近"的定义。

```
预警带 = 限制值的 X%，或绝对距离 X
```

> **推荐默认 · 2026-08-27**：WARNING 预警带 = **约束边界的 90%**。风控可改。
>
> **依据**：留出一期调仓的缓冲 —— 权重在调仓间隔内会因净值涨跌自然漂移，若在 100% 才告警，发现时往往已经越界。90% 使问题在**仍可通过正常调仓化解**时被发现。
>
> **预警不阻断**：90%~100% 之间是合规的，只是接近边界。阻断应发生在 100%（`VIOLATED`），预警的作用是让人提前知道。

## 8. 约束的模式适用性 ⚠️

> **沿用 `01-portfolio-construction` §11.2：并非所有约束在两种模式下都适用。**

| 约束 | `INITIAL` | `REBALANCE` |
|---|:---:|:---:|
| 单基金权重上下限 | ✅ | ✅ |
| 类别上下限 | ✅ | ✅ |
| 组合波动率上限 | ✅ | ✅ |
| 集中度上限 | ✅ | ✅ |
| **换手率上限** | **❌** | ✅ |
| **单笔最小交易量** | **❌** | ✅ |

> **首次建仓的换手率必然是 100%** —— 若套用换手率上限，新组合永远无法建仓。这必须在 `Constraint Policy` 中显式配置，而不是靠实现约定。

## 9. 约束的持续监控

### 9.1 满足过的约束会被重新违反

> **净值漂移会使已满足的约束重新被违反，即使没有任何交易。**

```
建仓时：Fund A 权重 8%，上限 10%           PASS
三个月后：Fund A 大涨，权重升至 11%         BREACH（未做任何交易）
```

**因此约束校验必须持续进行**，而非仅在决策时执行一次。

### 9.2 校验用哪个权重

> 沿用上游 ⑨-S 使用规则：

| 时点 | 使用的权重 |
|---|---|
| **决策时** | `Target Portfolio` |
| **持续监控** | **`Actual Portfolio`** |

> **不得以 `Target` 冒充 `Actual` 做合规监控** —— 那会得出"永远合规"的错误结论，因为 Target 本身就是按约束求解出来的。

### 9.3 漂移导致的 Breach 触发 `Constraint Breach` 类再平衡

> 按上游 ⑩-T，`Constraint Breach` 的重算范围是 **⑥ → ⑦（仅重新求解）** —— Universe 与 Score 不变。

## 10. Explainability

> **必须能回答：Which constraints are binding?**

### 10.1 紧约束是关键诊断信息

> 与 `03-portfolio-optimization` §10.2 同一原则。

```
约束校验报告：
  单基金上限 (Fund A)     Limit=X%  Actual=X%  Status=PASS  [BINDING]
  单基金上限 (Fund C)     Limit=X%  Actual=X%  Status=PASS  [BINDING]
  Equity 下限             Limit=X%  Actual=X%  Status=PASS  [BINDING]
  组合波动率上限          Limit=X%  Actual=X%  Status=PASS  （余量 X%）
  换手率上限              Limit=X%  Actual=X%  Status=PASS  （余量 X%）
```

> **`PASS` 且 `BINDING` 与 `PASS` 且有大量余量，是两种完全不同的状态** —— 前者正在实质性塑造组合，后者在本次求解中没有起作用。仅报告 `PASS` 会把两者混为一谈。

### 10.2 长期无余量与长期大量余量都值得关注

| 现象 | 含义 |
|---|---|
| 某约束长期 `BINDING` | 它是主要的限制因素；是否设置过紧值得复核 |
| 某约束长期有大量余量 | 它从未起作用；是否设置过松，或本就不必要 |

## 11. Edge Cases

| 情形 | 处理 |
|---|---|
| 约束缺 `scope` 或 `scope_key` | **不得进入约束集**（§2.2） |
| `Σ min > 100%` 或 `Σ max < 100%`（类别层） | **配置错误** —— 结构性不可行（`02` §7.2） |
| `min_weight × 最小持仓数 > 100%` | 同上 |
| 某类别有下限但 Universe 中无该类别基金 | 可行性预检失败，上报 Construction 层 |
| 校验所需数据不可得 | `NOT_AVAILABLE` → **阻断**（§6.3） |
| **冻结持仓导致约束违反** | 该 Breach **不可通过调仓消除**；须单独标注，不应反复触发无效的调仓尝试 |
| 首次建仓触发换手率约束 | 配置错误 —— 换手率约束不应适用于 `INITIAL`（§8） |
| 多条约束同时 `BREACH` | 全部记录（§6.4），按优先级向 Human Review 提供建议 |
| 合规约束 `BREACH` | **不可放松**（§5.3）；必须调整组合或中止本期 |

### 11.1 冻结持仓导致的 Breach 是一类特殊情形 ⚠️

```
Fund X 变为 NOT_TRADABLE，持仓冻结在 12%
单基金上限为 10%
    → BREACH，但既不能卖出也无法稀释（除非投入新资金）
    → 反复触发 Constraint Breach 类再平衡，每次都解不出可行解
```

**处理**：冻结持仓引起的 Breach 必须**单独标注为"不可消除"**，不进入再平衡触发判定，改为持续告警并上报。否则系统会陷入无效的重试循环。

> **已定案 · 2026-08-27**：标记 **`VIOLATED_BY_FROZEN`**，**不阻断决策**，须在决策记录中留痕。
>
> **依据**：不可交易是**外部事实**，不是决策错误。
>
> ```
> 一只基金暂停赎回 → 权重冻结 → 约束超限
>
> 若阻断决策
>     → 整个组合因一处外部状态而无法调整
>     → 而其余可交易部分本可以正常优化
>
> 若当作普通违反
>     → 决策记录中混入了非决策原因的违反
>     → 审计时无法区分「决策做错了」与「环境不允许」
> ```
>
> **处置流程**：①标记并记录冻结的持仓与冻结原因；②在**可交易的范围内**求解优化；③约束按可交易部分校验，冻结部分的贡献计入但不视为违反；④冻结解除后的下一个调仓日**自动纳入**正常约束校验。
>
> **须与 `AA-5` 保持一致** —— 类别层超限同样按此处理，不强制卖出其它成分。

## 14. Auditability

### 14.1 追溯链

```
Constraint Validation Result
    ├─ Constraint Policy Version   → 当时的约束定义与优先级
    ├─ 权重来源（Target 或 Actual）→ 校验对象
    ├─ Risk Model Version          → 风险类约束的 Σ
    ├─ 分组数据版本（PIT）          → GROUP 作用域
    └─ mode                        → 哪些约束适用
```

### 14.2 校验历史必须保留，而非只保留当前状态

> **约束校验的价值有一半在时序上。**

```
只保留当前状态："全部 PASS"
保留历史：       "某约束在过去 6 个月中有 4 次触及上限"
    → 后者才能回答"这条约束是否设置过紧"
    → 也才能发现"某约束从未起过作用"
```

（§10.2 的两类现象都需要历史数据才能识别）

### 14.3 放松决策必须留痕

> 第一阶段虽然 `Relaxation = OFF`，但 Human Review 中做出的约束调整（`03` §8.3 的"调整约束"分支）**必须升 `Portfolio Rule Version` 并记录原因**，而非直接改配置。

## 15. Summary

约束在**构建、优化、再平衡**三个环节都要满足，且**净值漂移会使已满足的约束重新被违反**。

三条定义要求：

- **每条约束必须声明 `scope` 与 `scope_key`** —— "Maximum Weight = 10%" 不说明 10% 是对什么而言，就无法校验也无法解释
- **约束必须区分 `INITIAL` 与 `REBALANCE` 模式** —— 首次建仓的换手率必然是 100%，套用换手率上限会使新组合永远无法建仓
- **最大回撤不得写入约束集** —— 它是路径依赖量，建仓时不可计算

三处判断：

- **第一阶段只实现 Hard Constraints，理由不是"简单"** —— Soft Constraint 需要一个惩罚系数，而该系数决定"违反多少约束换取多少目标改善算划算"，这是投资决策而非技术参数
- **优先级不等于自动放松许可** —— 它只为 Human Review 提供建议顺序；标记为合规的约束不进入放松候选
- **HHI 约束是凸的但会使问题变为 QCQP** —— "前 N 大合计" 是线性约束，业务含义也更直观，第一阶段优先使用

两处默认值与循环陷阱：

- **`NOT_AVAILABLE` 不得当作 `PASS`** —— 波动率算不出来不等于没超上限
- **冻结持仓导致的 Breach 不可消除** —— 若进入再平衡触发判定，系统会陷入"触发 → 求解 → 无解 → 再触发"的无效循环

## 16. Decisions

| # | 决策 | 理由 |
|---|---|---|
| D-1 | **每条约束必须声明 `scope` + `scope_key`** | 缺失则无法校验也无法解释 |
| D-2 | 区分 Constraint 与 Eligibility Rules | 前者作用于组合结构，后者作用于单只基金 |
| D-3 | **最大回撤不进入约束集** | 路径依赖，建仓时不可计算 |
| D-4 | **第一阶段只实现 Hard Constraints** | Soft 的惩罚系数是投资决策，无业务依据不得由实现者决定 |
| D-5 | **优先级仅为 Human Review 提供建议顺序** | 第一阶段 Relaxation = OFF |
| D-6 | **合规约束不进入放松候选** | 放松合规不是投资决策 |
| D-7 | **`NOT_AVAILABLE` 必须阻断** | "不知道"≠"没问题" |
| D-8 | 全部约束必须校验，**不得短路** | 否则丢失"还违反了哪些" |
| D-9 | **约束须声明模式适用性** | 换手率约束不适用于首次建仓 |
| D-10 | 持续监控使用 `Actual`，决策时使用 `Target` | 用 Target 做合规监控会得出"永远合规" |
| D-11 | **紧约束必须在校验报告中标注** | `PASS+BINDING` 与 `PASS+大量余量` 是不同状态 |
| D-12 | **冻结持仓引起的 Breach 标注为"不可消除"，不进入再平衡触发** | 否则陷入无效重试循环 |
| D-13 | 集中度优先使用"前 N 大"线性形式而非 HHI | 线性约束更易求解，业务含义更直观 |
| D-14 | `GROUP` 作用域的分组数据必须 PIT | 管理人变更会改变分组 |
